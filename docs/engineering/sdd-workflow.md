# SDD 开发工作流

> 状态：已采用  
> 适用范围：所有新增公共行为、跨包接口和核心业务变更

## 1. 开发入口

开始任务前依次读取：根 `AGENTS.md`、工程约定、全局架构、相关 Accepted ADR、功能 SDD `README.md`、当前任务、关联契约与测试、`status.md`。

## 2. 准入条件

公共行为开始实现前必须具备：稳定需求 ID、模块映射、输入输出契约、错误语义、任务 ID、关联测试和回滚原则。缺少必要规格时先补规格，不凭实现者经验临时决定。

纯内部重构可以使用精简规格，但必须写明行为不变的判断依据、影响范围和回归方式。紧急修复可以先恢复服务，但必须保留问题、验证和后补规格任务，不能以紧急为由永久跳过追踪。

## 3. 工作阶段

1. **规格准备**：确认需求、ADR、契约、状态机和测试可执行；
2. **任务认领**：记录任务 ID、允许/禁止修改范围、依赖和 DoD；
3. **实现**：从公共契约开始，小步修改，遵守模块依赖；
4. **验证**：运行任务关联的单元、类型、构建、集成和人工验收；
5. **同步**：更新 tasks、traceability、status 和必要规格；
6. **阶段验收**：生成 deliverable，记录实际结果和未完成项。

任务应满足：单一目标、修改边界明确、依赖可识别、完成条件可验证、失败后可回滚。一个任务若需要同时改变多个独立领域，应继续拆分。

## 4. 变更纪律

- 实现与规格冲突时，先修改规格并完成必要评审；
- Accepted ADR 的结论不能原地反转，应新增 ADR 标记替代关系；
- 没有关联测试的公共行为任务不能标记完成；
- 文档完成不等于代码完成，代码完成不等于已验证；
- 只实现任务授权范围，发现相邻问题应新增任务或报告，不顺手扩大重构；
- 阶段评审报告是冻结快照，后续变化通过新报告或变更记录表达。

## 5. 完成状态

统一使用：`草案`、`待评审`、`已接受`、`实施中`、`已实现`、`已验证`、`已废弃`、`已替代`。任务可以使用：`待开始`、`进行中`、`阻塞`、`待验收`、`完成`、`取消`。

## 6. 提交前检查

- 需求、任务、测试编号可互相追踪；
- 公共 Schema 位于 `@openclawx/contracts`；
- 模型 SDK/HTTP 只在 `packages/agent-core`；
- 编排状态归 `@openclawx/orchestrator`；
- renderer 不依赖 Node/Electron 或秘密配置；
- 已执行对应测试并在 status/deliverable 记录事实；
- 未覆盖用户无关改动。

## 7. 规格变更影响分析

需求、契约、状态机或安全边界变化时，至少检查：调用方、持久化数据、配置迁移、事件消费者、UI 状态、工具权限、监控指标、回归套件、部署与回滚。影响分析应记录在 plan、tasks 或 ADR 中，而不是只存在于评审对话。
